# Local engine migration — Task 2 PTY helper (Gate C, in progress)

**Status: NOT PASSED. Blocked on a Zig build input, with the blocker identified precisely.**
**Branch:** `local-engine/task-0`.

## What Task 2 has to achieve

Produce a target-specific PTY binary from the vendored source, repoint the CLI build and the core
PTY binding at it, and remove the eager registry lookup. Gate C: "CLI compilation and PTY
execution can use the validated local helper with registry PTY packages absent."

## The failing case was established before the fix

The plan requires confirming that the original eager `createRequire` fails. Reproduced against the
vendored tree, with `@opencode/pty` absent from `node_modules`:

```
$ bun /tmp/probe-pty.ts
EAGER RESOLUTION FAILED: Cannot find module '@opencode/pty/package.json'
```

And the registry dependency is real, not hypothetical — three vendored manifests declare it:

| Manifest | Field |
| --- | --- |
| `packages/core/package.json` | `dependencies` |
| `packages/cli/package.json` | `dependencies` |
| `packages/server/package.json` | `devDependencies` |

It is in `bun.lock` with all eight platform variants. So this is a genuine removal, not a
cosmetic one.

## What was changed

**`packages/core/src/persistent-pty/local-pty.ts`** (new) — supplies what `@opencode/pty`
supplied: a local artifact path, its version and its SHA-256, plus the `binaryPath` shape the
binding consumed. It fails loudly when no local artifact exists rather than falling back to a
registry package or a bare `opencode-pty` on `PATH` — a fallback would make the build appear to
work while silently retaining the dependency the migration exists to remove. `BASHWINK_PTY_DIR`
is the single seam the build and the packaged launcher share, so a build cannot embed one helper
while the runtime launches another.

**`packages/core/src/persistent-pty/pty-binding.ts`** — imports the local module instead of
`@opencode/pty`. Deliberately **not** a re-export shim: a shim would put the dependency straight
back. The `binding` export shape is unchanged, so `binary.bun.ts` and its `install()` path — which
already validates a digest and refuses symlinks or foreign-owned files — keeps working untouched.

**`packages/cli/script/opencode-pty.ts`** — removes both eager `createRequire` calls, which were
the reason the module threw at import time rather than at use time. It now resolves
`OPENCODE_PTY_BIN` or `BASHWINK_PTY_DIR`, derives the binary name from the **target** rather than
the host so a cross-target build cannot pick up the host's helper, and raises a message naming the
build command when the artifact is missing.

Existing `OPENCODE_PTY_BIN` support is preserved, including its restriction that an explicit
override may only be embedded in a build for its own platform and architecture — a cross-platform
embed would ship the wrong executable.

## Where the build stops, and why

```
$ cd vendor/engine/packages/process-daemon
$ cargo build --locked --release
   ... fetch https://github.com/ghostty-org/ghostty.git ab0b9da9e88fcb4b0533a1854e84628f663930af
   thread 'main' panicked at build.rs:149:33:
   cd ".../ghostty-ab0b9da..." && "zig" "build" ... : No such file or directory (os error 2)
BUILD EXIT=1
```

Two distinct facts, and only one of them is a blocker:

**1. Rust version — resolved.** `packages/process-daemon/rust-toolchain.toml` pins
`channel = "1.90.0"`, and this host had 1.95.0 and stable only. Rust **1.90.0 was installed**
(`rustup toolchain install 1.90.0 --profile minimal`, exit 0) and is now active, so
`cargo build --locked` runs against the pinned compiler rather than whatever was lying around.

**2. Zig — the blocker.** `build.rs` shells out to `zig build` to compile Ghostty's VT library.
The plan pins **Zig 0.16.0** for the daemon and Zig is not installed on this host. This is exactly
the Gate C risk recorded in the Task 0 baseline; it is now a measured blocker rather than a
prediction. Zig 0.16.0 is being fetched from `ziglang.org` (the plan's stated source).

Note there are **two different Zig pins** in this project, and conflating them would be a mistake:

| Use | Zig version | Source |
| --- | --- | --- |
| `process-daemon` / Ghostty VT | **0.16.0** | plan, §Source and platform pins |
| OpenTUI no-FFmpeg rebuild (Task 3) | **0.17.0** | `release/NOFFMPEG_RUNTIME.md` |

Homebrew offers 0.17.1, which is neither pin, so it was not used. A build with the wrong Zig
version is not a slower build — it is a build whose output cannot be attributed to the pin.

## A second build-input finding: the build fetches Ghostty from the network

`build.rs` performs `git init` + `git fetch --depth=1` of
`https://github.com/ghostty-org/ghostty.git` at the pinned revision, unless `GHOSTTY_SOURCE_DIR`
is set. This is upstream's own behaviour, not something introduced by this migration, and
upstream has a `prefetch-ghostty` composite action that sets `GHOSTTY_SOURCE_DIR` and caches Zig
packages for exactly this reason.

**It still matters for the plan's constraints.** "The final build … require no OpenCode registry
artifacts or executable on PATH" is satisfied — Ghostty is not an OpenCode artifact. But "Resolve
each build input to a pinned, reviewable source" is only *partly* satisfied by a `git fetch` at
build time: the revision is pinned, the transport is not. For a reproducible build this belongs
behind a prefetch step with a recorded digest, mirroring upstream's own action. Recorded as a
build-input gap to close before Gate D, not as a Task 2 failure.

Also noted: Zig's own package cache (`p/`) is content-addressed and populated over the network on
first build. That is a third unpinned transport in the native build, and the same prefetch/cache
treatment applies.


This closes the unpinned-transport gap noted above for this run: the build now consumes a reviewed

the checkout — so a CI or contributor build still needs a documented prefetch step. That remains
open for Gate D.

## A defect introduced and caught before commit

The first version of `resolveOpencodePty` returned the **host's** helper for any target, so a
`linux-x64` build would have embedded an arm64 Mach-O binary and labelled it Linux — a build that
succeeds and ships an unrunnable executable. Found by probing the resolver with
`{platform: "linux", arch: "x64"}` against a darwin-arm64 artifact directory. Fixed to refuse a
cross-target reuse with a legible message. All three cases now verified:

```
darwin-arm64 -> RESOLVED v0.6.0 sha=9a82311b4909
linux-x64    -> REFUSED: BASHWINK_PTY_DIR holds the darwin-arm64 helper, but this build targets…
no artifact dir -> undefined   (never a PATH or registry fallback)
```

- **Repo self-containment**: the Ghostty prefetch lives outside the checkout, so a fresh clone
  still needs a documented prefetch step before Gate D.
