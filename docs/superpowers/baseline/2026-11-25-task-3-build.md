## 1. PTY input and output — proven by an existing Cargo test

The plan asks for an existing test, and there is a precise one. Not a mock, not a fixture that
asserts on its own plumbing — a real child process on a real PTY, both directions:

`vendor/engine/packages/process-daemon/tests/runtime.rs:30`
**`real_child_input_output_unicode_and_snapshots`**

What it does, in its own terms:

```rust
let info = service.create_pty(fixture.request()).unwrap();
assert!(info.pid.is_some_and(|pid| pid != 0));
let mut child = fixture.connect();
child.command(Command::Output("\x1b[2J\x1b[Hplain café 界 🙂\r\nREADY".into()));
let snapshot = wait_text(&service, info.id, "READY");
assert!(snapshot.text.contains("plain café 界 🙂"), "{snapshot:?}");
assert!(!snapshot.checkpoint.is_empty());
let rows = service.read_rows(info.id, None).unwrap();
assert!(rows.lines.iter().any(|line| line == "plain café 界 🙂"));
assert_eq!((rows.cursor_x, rows.cursor_y), (5, 1));
let input = "typed café 界 🙂\r".as_bytes();
service.write(info.id, input.to_vec()).unwrap();
assert_eq!(child.command(Command::Read(input.len())), serde_json::json!(input));
```

**Output direction:** a real child writes to the terminal; the service observes it through three
independent surfaces — a text snapshot, a checkpoint, and a cell-grid read — and the cursor position
after a clear-and-home escape is asserted exactly, so the snapshot cannot be a naive byte capture.

**Input direction:** bytes written to the service arrive verbatim in the child, unicode intact.

**Clean close:** `service.terminate(info.id).unwrap()`.

Run, by name, with the pinned toolchain:

```
$ cargo test --locked --release --test runtime real_child_input_output_unicode_and_snapshots
running 1 test
test real_child_input_output_unicode_and_snapshots ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 8 filtered out; finished in 0.06s
EXIT=0
```

This closes the gap the Task 2 record left open ("the PTY data path itself remains unexercised"). It
is a stronger proof than the open-a-terminal-and-type check that was the alternative: it asserts on
the grid and cursor, not just on echoed text, and it covers the unicode path that a naive shell
roundtrip would miss.

Two related tests exercise the same service and were part of the 145/0 suite already recorded:
`child_cwd_environment_and_quoted_program_path` (cwd, env, argv quoting including an empty argument
and a trailing backslash) and `executable_is_resolved_from_child_path`.

**Scope of this proof:** darwin-arm64 only, and it is a test fixture child rather than the OpenCode
TUI. It establishes the PTY layer works; it does not establish that the engine, once built, drives
it correctly. That is Gate D/E work.


Every case failed for the honest reason, which is what the plan asks for.

**After:** `Ran 13 tests ... OK`, exit 0.

| Group | What it refuses |
| --- | --- |
| UnsupportedTarget | an unknown target by name, and never substitutes the host's target for one |
| MissingInput | a missing engine/helper, with no URL in the message (no download invitation) |
| DigestMismatch | a wrong PTY digest — "refused, never trusted" |
| NonLocalPty | a binary named `opencode-pty` that is merely on `PATH`; a registry source kind |
| PathContainment | `../..` traversal, **and a symlink inside the root pointing outside it** |
| DownloadFallback | any request to download a published runtime; also asserts no fetch helper exists |
| ManifestShape | the plan's required keys; digest stability across key order |

The symlink case is the one worth having. The path *string* is inside the build root; only the
resolved path escapes. A builder that checked the string and copied the file would ship a file from
outside the build root while passing a naive containment test.

**Two failures were mine, and were fixed rather than accommodated:**

- `manifest_for_target("plan9-mips")` raised correctly, but `to_opencode_target` was calling a
  helper with a typo'd name (`SUPORTED_TARGETS_get`) and assigning it into a local as a side effect.
  Rewritten.
- The digest test failed because `preflight()` ran before the PTY digest check, so the error was
  "an OpenTUI library is missing" when the real fault was a wrong digest. Reordered so the specific
  fault is reported — and the reason is commented, because the ordering looks arbitrary otherwise.
- One assertion of mine was simply wrong: it looked for `source` among the top-level required keys
  when the manifest records it inside `pty`. The assertion now checks the produced manifest. The
  contract is unchanged; the test was corrected to test it.

## 3. Ghostty: reproducible from a clean clone

This was the gap recorded at Gate C — the build's inputs were decided by the build, via a `git
fetch` inside `build.rs`, with no integrity record.

`scripts/fetch_native_inputs.py` closes it:

- reads the revision from `vendor/engine/packages/process-daemon/ghostty-revision` — **the pin lives
  in the vendored tree and is not restated here**, so a stale constant cannot mask a changed pin;
- fetches `--depth=1` at that revision, verifies `rev-parse HEAD` equals it, and refuses otherwise;
- computes a **tree digest** over every file (paths + per-file sha256, sorted), written to a
  `.bw-complete` marker;
- `--check` recomputes and compares; `--env` prints the exports the build needs;
- deletes a half-finished checkout rather than reusing it, because a partial tree that happens to
  satisfy a build is worse than none.

```
$ python3 scripts/fetch_native_inputs.py --fetch
ghostty ab0b9da9e88fcb4b0533a1854e84628f663930af -> …/native-inputs/ghostty-ab0b9da…
treeDigest 97f52c3043cf4cad00abde4f3789a8c7392567c8b74f6036c4f5db198fd883b1

$ python3 scripts/fetch_native_inputs.py --check      # twice, stable
run1 digestMatches = True   run2 digestMatches = True
stable across runs = True
```

**A self-invalidating digest, caught and fixed.** The first version computed the tree digest and
*then* wrote the marker into that same tree, so the marker's own bytes changed the next digest — every
subsequent `--check` reported a mismatch against a value that was correct when written. The marker is
now excluded by name, with the reason in the docstring.

**The tamper control was wrong twice before it was right**, and both failures were informative:

1. First attempt appended to `ghostty/VERSION`, which **does not exist** in this checkout. `cp`
   failed, nothing was tampered with, and `digestMatches = False` was read from a tree that was
   already inconsistent — a test that proves nothing while appearing to prove the point.
2. The stray `VERSION` file created by that attempt then genuinely polluted the tree, so the
   *baseline* started failing. Removed it, confirmed `digestMatches = True`, then tampered
   `build.zig` for real: `False`, restore, `True`. Only the third version of the experiment
   establishes anything.

Recorded because "I ran a negative control" and "the negative control was valid" are different
claims, and this one took three attempts.

## 4. Zig: two pins, deliberately kept apart

| Use | Version | Why it cannot be substituted |
| --- | --- | --- |
| `process-daemon` PTY helper (Ghostty VT) | **0.16.0** | `build.rs` shells out to a bare `zig`; the built helper is already pinned by sha256 |
| OpenTUI native library rebuild | **0.17.0** | `opentui/packages/native/build.zig` requires it (`release/NOFFMPEG_RUNTIME.md`) |

Homebrew's only offering was 0.17.1 — **neither pin** — so it was not used for either. The daemon is
built with 0.16.0 (already done, `9a82311b…`); OpenTUI will be built with 0.17.0. They are separate
toolchains on purpose: one build, one pin, no shared "close enough" version.

`fetch_native_inputs.py --env` exports `PATH` with the 0.16.0 Zig first for the daemon. The OpenTUI
step will use an explicit 0.17.0 path, never the ambient one.

## 5. What is not done

- **The engine is not built.** `scripts/build_local_engine.py` validates, refuses and writes a
  manifest, but has not yet driven `build.ts` to completion. Zig 0.17.0 is still downloading; without
  it the OpenTUI rebuild produces either a stock FFmpeg-containing library or nothing.
- **No manifest with real engine digests exists yet.** `build/engine/<target>/engine-manifest.json`
  will carry `engine.sha256 = null` until the build runs, and a null digest must not be read as a
  pass.
- **Windows x64 is unstarted and unverifiable here.** There is no Windows host. The target name
  translation (`win32-arm64` → `windows-arm64`) is implemented and unit-tested, and `preflight()`
  looks for `opencode-pty.exe`, but nothing has been built or run on Windows. Per the plan this
  belongs to Task 7's matrix; it is logged as unverified rather than attempted.
- **Licensing gate is not run.** The plan requires native libraries to be compared against the
  published notice inventory using the full gate, not a string search. That has not happened.
- **Installer untouched.** It still selects the current runtime; cutover waits for Gates D–E.
